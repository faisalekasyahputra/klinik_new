## 1. AUTH & SIKLUS AKUN (login, register, onboarding, Google OAuth, dashboard /akun, update profil, hapus akun)

### Ringkasan

Subsistem terdiri dari Auth.php (login email/username+password dengan rate-limit 5x/15 menit di Auth_model, Google OAuth popup dengan state token bin2hex(random_bytes(16)) + hash_equals, register 2 jalur: umum dan "daftar cepat" SRP2, onboarding multi-role, verifikasi email SIMULASI, hapus akun via Pengaturan), Pengaturan.php (route akun = daftar status semua pengajuan by user_id sesi; akun/profil = edit profil + password + data SRP2 + hapus akun), User_Profile.php (sudah diarsipkan, tinggal redirect ke akun/profil), Auth_model (lookup, lockout, ensure_srp2_draft idempotent satu-satunya pembuat draft SRP2, token email/reset yang TIDAK pernah dipakai), User_model (check_google_user auto-link by email, update_user sinkron nama forum, delete_user_account: unlink file privat srp2/kemitraan/onboarding SEBELUM delete, anonimisasi forum, hapus likes, lalu delete usr_users → FK CASCADE membersihkan srp2_registrations+srp2_documents, kkn_magang_pendaftaran, usr_documents; aduan & sf_housing_queue SET NULL). Kolom usr_users yang dipakai: id, google_id, name, username, email, password, avatar, email_verified_at, email_token, email_token_expiry, role, profile_completed, status, login_attempts, locked_until, phone, created_at, updated_at, nik (AES-256-GCM), nik_lookup_hash, kategori, alamat, nama_perusahaan, alamat_kantor, telp_kantor, kabupaten_id (migrasi 08), bidang_kode (migrasi 09). Isi session login: user_id, name, username, email, avatar, role, kabupaten_id, bidang_kode, is_logged (+ transien: intended_url, oauth_state, oauth_redirect, srp2_quick_registration, srp2_verify_pending). Fondasi keamanan inti sehat: CSRF global aktif (csrf_regenerate=FALSE sehingga hash bisa dipakai ulang wizard AJAX), sess_regenerate(TRUE) setelah login, anti-IDOR konsisten (user_id selalu dari sesi), sanitize_redirect anti open-redirect dipakai di next/redirect_to/from/curr, upload onboarding sudah lewat store_private_upload (whitelist ekstensi + finfo MIME + nama acak) ke private_uploads di luar webroot/berpagar .htaccess. Kondisi umum: sehat di jalur utama, tapi ada beberapa bug nyata di jalur pinggir (onboarding vendor menulis kolom yang tidak ada, hapus-akun macet untuk akun daftar-cepat SRP2 tanpa nama/username, potensi draft SRP2 dobel via Auth/lanjutkan) dan risiko keamanan yang perlu keputusan (kotak kredensial demo tampil di semua lingkungan termasuk production, XSS potensial di echo JS google_callback, ganti password/hapus akun tanpa re-autentikasi). Lupa password murni placeholder; seluruh mekanisme token email/reset adalah kode mati.

### Alur penting

- Login form/AJAX: do_login → find_by_login (email ATAU username) → cek lockout (5x gagal = kunci 15 menit) → password_verify → reset attempts → session {user_id,name,username,email,avatar,role,kabupaten_id,bidang_kode,is_logged} + sess_regenerate(TRUE) → ensure_srp2_draft jika role pengembang → AJAX: JSON (role, registration_id, dashboard_url) / non-AJAX: _redirect_after_login (onboarding jika profile_completed=0, lalu intended_url dari session, lalu beranda).
- Registrasi umum: do_register → validasi email+kekuatan password (8+/kapital/angka/simbol) + reCAPTCHA opsional → create_user (status restricted, role NULL) → auto-login → verify_pending (simulasi progress) → do_verify_email (set email_verified_at tanpa email nyata) → lanjutkan → onboarding.
- Registrasi cepat SRP2 (wizard Pengembang/syarat via AJAX): do_register dengan srp2_pengembang=1 + nama_perusahaan → role langsung 'pengembang', profile_completed=1, status active, draft srp2_registrations dibuat saat itu juga → JSON registration_id → wizard lanjut ke unggah dokumen tanpa pindah halaman (tanpa onboarding, tanpa NIK/nama).
- Onboarding (jalur umum & user Google): pilih role warga/pengembang/vendor/mahasiswa → username unik + NIK 16 digit dienkripsi AES-256-GCM + deterministic hash → save_profile (profile_completed=1, active) → ensure_srp2_draft jika pengembang → _handle_uploads simpan KTP/SIUP/KTM/surat via store_private_upload ke private_uploads/onboarding/{user_id}/ (jalur vendor RUSAK: kolom DB tidak ada).
- Google OAuth: google() simpan state token + oauth_redirect (sanitize_redirect dari ?from=) → google_callback validasi hash_equals state → check_google_user auto-buat/link akun by email → tandai email terverifikasi → session lengkap + sess_regenerate → jika profile_completed=0 arahkan onboarding → ensure_srp2_draft jika pengembang → echo JS window.opener redirect (titik XSS potensial).
- Dashboard /akun: Pengaturan::index() agregasi sf_housing_queue + aduan (+catatan_admin) + srp2_registrations (pengembang, baris terbaru) + kkn_magang_pendaftaran (mahasiswa) semua WHERE user_id sesi, urut tanggal desc, render lewat shell dashboard terpadu render_user_dashboard().
- Update profil: akun/update (nama/username unik/phone/password opsional dengan aturan kekuatan sama, TANPA cek password lama) + akun/update_pengembang (data perusahaan SRP2, WHERE user_id dari sesi, whitelist asosiasi) → sinkron session name/username → sinkron nama di forum_diskusi/forum_komentar via update_user().
- Hapus akun: akun/delete (POST-only + CSRF, konfirmasi ketik-nama hanya klien) → delete_user_account: unlink file privat (srp2 per registration_id, kemitraan per id pendaftaran, onboarding per user_id — path dari helper private_upload, basename() anti-traversal) SEBELUM transaksi → anonimisasi forum ('Akun Dihapus') → hapus forum_likes → DELETE usr_users → FK: srp2_registrations+srp2_documents & kkn_magang & usr_documents CASCADE, aduan & sf_housing_queue SET NULL → sess_destroy → redirect login.

## 3. FORUM, ADUAN & CHAT

### Ringkasan

Subsistem terdiri dari tiga bagian dengan tingkat kesehatan sangat berbeda. (1) FORUM (Umum.php + Forum_model + forum_helper, UI direbrand jadi "Konsultasi Terjadwal"): thread di forum_diskusi, komentar flat di forum_komentar dengan kolom reply_to lalu dirakit jadi pohon nested rekursif di view forum_detail.php; likes di forum_likes (UNIQUE per user+target) dengan counter denormalisasi like_count via toggle_like; moderasi admin (status open/resolved/closed, soft-delete) plus auto-hide konten yang dilaporkan >= 5x. Escaping XSS konsisten (htmlspecialchars hampir di semua output user), guard login untuk posting, profanity filter + whitelist kategori. TAPI rate-limit helper menghitung ke tabel 'diskusi'/'komentar' yang tidak ada (tabel nyata forum_diskusi/forum_komentar) sehingga tambah topik & balas kemungkinan besar fatal error, dan report_komentar bisa dipakai tanpa login tanpa dedup untuk menyembunyikan komentar siapa pun (5x POST). (2) ADUAN (Umum::aduan/simpan_aduan + Aduan_model): paling sehat — validasi form ketat (whitelist bidang in_list), user_id selalu dari sesi (tamu NULL), lampiran lewat store_private_upload (whitelist ekstensi + finfo MIME + 5MB + nama acak) ke private_uploads/aduan/{id}/ di luar webroot, disajikan hanya lewat endpoint ber-guard Admin_Aduan/Admin_Bidang::lihat_lampiran (WHERE ganda bidang untuk admin scoped); admin view escape dengan html_escape. Catatan: AGENTS.md §17 masih mengklaim upload aduan di direktori publik — usang. (3) CHAT (Chat.php + widget global di layouts/footer.php): paling tidak sehat — sebenarnya chatbot Gemini murni (bukan konsultasi manusia; label 'Petugas' di JS dead code), menulis ke tabel tb_chat yang TIDAK ada di schema baseline maupun migrasi mana pun; Chat_model (yang memakai chat_rooms/chat_messages sesuai dokumentasi) di-load tapi tidak pernah dipanggil; session_id dibuat klien pakai Math.random tanpa ikatan sesi server sehingga riwayat chat + PII (nama/email/hp) bisa dibaca siapa pun yang tahu token; ketiga endpoint chat dikecualikan dari CSRF, tanpa login, tanpa rate limit, dan api_bot() public-routable — kuota Gemini bisa dikuras siapa pun. Polling klien tiap 3 detik (bukan websocket). Kesimpulan: aduan sehat, forum sehat-tapi-patah-di-rate-limit, chat perlu dirombak (skema, otentikasi token, rate limit).

### Alur penting

- Forum (UI: 'Konsultasi Terjadwal'): Umum::forum → Forum_model::get_all_diskusi (LEFT JOIN hitung balasan, filter q/kategori, exclude is_deleted) → forum.php; buat topik via modal POST Umum::tambah_aksi dengan gate login + rate limit (RUSAK: tabel salah) + whitelist kategori + profanity check → insert forum_diskusi dengan identitas dari session.
- Detail thread: Umum::detail/{id} → increment view_count → get_komentar_by_diskusi mengambil komentar FLAT lalu view forum_detail.php merakit pohon nested by-reference dari kolom reply_to dan merender rekursif (render_thread); balas via POST balas_aksi (login, role komentar 'Petugas Disperakim' ditentukan backend utk admin) — tanpa validasi diskusi eksis/closed.
- Likes: AJAX POST Umum::toggle_like (login, CSRF dari halaman) → Forum_model::toggle_like insert/delete forum_likes + update counter denormalisasi like_count di forum_diskusi/forum_komentar; status like awal user dikirim ke view via get_user_likes.
- Moderasi: report_komentar (AJAX, TANPA login) menaikkan report_count lalu auto_hide_reported men-soft-delete konten dengan >=5 report; update_status/delete oleh _check_admin (cek session role hardcode, bukan base controller).
- Aduan: GET umum/aduan (form publik prefill session) → POST umum/simpan_aduan (form_validation + in_list bidang; user_id dari sesi atau NULL utk tamu) → Aduan_model::create baris dulu → lampiran opsional via MY_Controller::store_private_upload ke private_uploads/aduan/{id}/ (finfo MIME + 5MB + nama acak, .htaccess deny otomatis) → update kolom lampiran; lampiran HANYA tersaji lewat Admin_Aduan::lihat_lampiran (superadmin) atau Admin_Bidang::lihat_lampiran (WHERE id + bidang sesi, anti-IDOR).
- Chat: widget global layouts/footer.php di semua halaman publik → pre-chat form POST Chat/register_session dengan session_id buatan klien (Math.random, disimpan localStorage) menyimpan pesan pertama + PII ke tb_chat → tiap pesan berikutnya POST Chat/kirim_pesan_lanjutan menyimpan pesan warga, memanggil Gemini (api_bot, system prompt pembatas topik), menyimpan jawaban sebagai 'bot' → klien polling POST Chat/ambil_pesan tiap 3 detik (setInterval) merender ulang seluruh riwayat; ketiga endpoint bebas CSRF, tanpa login, tanpa rate limit; Chat_model/chat_rooms/chat_messages sama sekali tidak dipakai.

## 6. Panel Admin & Dashboard Terpadu (base controller hierarchy, registry dashboard_modules, controller Admin_*, model Admin/Setting, view shell admin + komponen bersama)

### Ringkasan

Subsistem ini SEHAT secara arsitektur dan sebagian besar klaim AGENTS.md terbukti benar di kode. Hierarki base controller di MY_Controller.php persis seperti didokumentasikan: MY_Controller (security headers tiap request, helper session, sanitize_redirect) → Public_Controller (tanpa guard), Admin_Controller (guard role 'admin' di constructor), Admin_Kabkota_Controller (guard role + kabupaten_id dari SESSION, redirect kalau scope kosong), Admin_Bidang_Controller (idem untuk bidang_kode). Ketiga render helper (render_admin/render_scoped_admin/render_user_dashboard) TERBUKTI semuanya delegasi ke satu method render_user_dashboard() yang membangun menu dari dashboard_menu() → registry application/config/dashboard_modules.php (filter role+scope, badge via count_pending_modul yang membaca table+pending_where, active-state match-terpanjang dihitung di controller bukan view) lalu merender shell admin/index.php (head+sidebar+topbar+content+footer). Registry murni mengatur menu TAMPIL; otorisasi ada di constructor — fail-closed, sesuai dokumen. Pola tabel admin konsisten di semua modul: table_state() (sort di-whitelist ketat, nilai ?sort= di luar whitelist jatuh ke default; pencarian via like() ter-escape) → filter → count_all_results('', FALSE) → paginate_state() (page di-clamp) → get(); link lewat admin_table_url()/admin_sort_header() sehingga filter/cari/urut saling terbawa dan kolom non-whitelist tidak pernah jadi link sort. Anti-IDOR admin ter-scope benar: Admin_Kabkota/Admin_Bidang update pakai pre-check keberadaan dalam scope (count) lalu UPDATE dengan WHERE ganda id+scope; lampiran juga WHERE ganda dan disajikan via serve_private_file ber-guard. Admin_Users memvalidasi kabupaten_id/bidang_kode ke tabel kabupaten/bidang untuk create_staff/update_role, role dari config/roles.php. Admin_Dashboard membangun kartu dari registry (entri ber-'ringkas') dengan angka hasil query nyata semua. Ada satu controller yang TIDAK tercantum di AGENTS.md: Admin_Aduan.php (superadmin read-only lintas bidang, sengaja tanpa endpoint tulis, plus deteksi 'bidang tanpa admin'). KONDISI TIDAK SEHAT yang tersisa: (1) halaman Admin_Settings (admin/settings/index.php) masih SEPENUHNYA mockup — nilai hardcode, form tanpa action/name, tombol Simpan & toggle maintenance tidak berfungsi — pelanggaran langsung protokol 'jangan tampilkan angka/status karangan'; (2) Admin_Content::update() meneruskan seluruh POST (termasuk token CSRF) ke sys_settings tanpa whitelist kunci; (3) logo sidebar hardcode ke Admin_Dashboard sehingga role non-admin diusir dengan flash 'Akses ditolak'; (4) view Admin_Users tidak memasang toolbar cari/sort padahal controllernya sudah siap; (5) perubahan role/scope tidak menyentuh session user target (revokasi tidak instan); (6) sisa elemen dekoratif di topbar (titik merah lonceng hardcode, search ⌘K tanpa handler) dan footer (link '#').
